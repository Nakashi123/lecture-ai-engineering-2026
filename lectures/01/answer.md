## 演習

- 講座に固有の質問（宿題の3レベル）へのモデルの回答（要約でよい）：講座固有の「宿題の3レベル」に対するGeminiの回答はまだ取得していない。なお、一般用語「LoRAとは何ですか？」については、Gemini APIへの接続と応答が得られることをCodespaces上で確認した。ただし、回答にはLoRAを別の意味で説明する不正確な内容が含まれていた。
- 用語集の正しい意味と比べて気づいたこと：`data/glossary.json` の `homework-levels` では、「基礎（講義内容の確認）」「実装（自分でコードを書く）」「発展（調査や試行）」の3段階とされ、どれか1つで完了となる。モデルの実回答との比較は未実施なので、正誤は判定していない。
- 表示できたトークン数（入力 / 出力）：実際のAPIによる計測値は未取得。`response.usage_metadata` の入力・出力トークン数を表示する処理を追加し、テスト用データ（入力123、出力45）が表示されることを確認した。この数値は実測値ではない。

## 宿題

- **取り組んだレベル：実装**
- **やったこと：** `app/ask.py` に `--chat` オプションを追加した。従来の1回質問モードは残したまま、会話モードでは、質問とモデルの回答を `history` に順番に保存し、次の `generate_content` 呼び出しに履歴全体を渡すようにした。終了コマンドや空入力への対応も入れた。また、演習で求められた入出力トークン数の表示も追加した。
- **結果：** APIを使わないローカルの模擬テストを5件実行し、5件とも成功した。特に、1回目の送信内容が「user」、2回目が「user → model → user」の順になること、前の質問と回答が次の入力に含まれること、空の回答は履歴に追加しないことを確認した。提出前のCodespacesでは、変更前の既存テスト11件の成功と、1回質問によるGemini APIへの接続を確認した。一方、変更後の会話モードについてのGemini APIでの連続質問と実際のトークン数表示は、まだ検証できていない。
- **使用モデル：** 講座リポジトリの `app/config.py` に設定された既定モデルは `gemini-3.5-flash-lite`。上記の単発質問はGemini APIを呼び出しているが、実際の実行モデル名は画面から確認できていない。会話履歴の機能テストでは固定の模擬回答を使用した。
- **気づき・疑問：** 会話履歴を明示的に渡すと、前のやり取りを踏まえた続きの質問ができる構造になる。一方、過去の会話を参照できることと、講座固有の事実を正しく回答できることは別で、必要な情報を検索して渡す仕組み（RAGなど）も重要だと考えた。履歴が長くなると入力トークン数や費用にどう影響するかは、今後実測して確かめたい。

### 実行方法

```bash
uv run python -m app.ask --chat
```

会話モードで「終了」または `exit` と入力すると終了する。なお、実際のGemini APIによる確認を行うには、Codespaces secret `GEMINI_API_KEY` の設定が必要。
